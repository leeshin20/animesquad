# 신규 가입 초대코드 설계

## 목적

베타 기간 동안 기존 사용자의 로그인은 그대로 유지하면서, 새로운 Google 계정의 가입만 공용 초대코드로 제한한다. 초대코드가 확인되기 전에는 사용자 레코드와 정식 로그인 토큰을 만들지 않는다.

## 범위

- 기존 사용자는 초대코드 없이 Google 로그인을 계속 사용한다.
- 신규 사용자는 Google 인증 후 초대코드 화면을 거친다.
- 공용 초대코드는 Render의 `INVITE_CODE` 환경변수로 관리한다.
- `INVITE_CODE`가 없거나 비어 있으면 신규 가입을 차단한다.
- 관리자용 초대코드 발급·회수 화면과 사람별 일회용 코드는 만들지 않는다.

## 사용자 흐름

### 기존 사용자

1. 사용자가 Google 로그인을 시작한다.
2. Google 인증 성공 후 `googleSub`로 기존 사용자를 조회한다.
3. 기존 사용자가 있으면 현재와 동일하게 정식 JWT 쿠키를 발급한다.
4. 온보딩 완료 여부에 따라 기존 목적지로 이동한다.

### 신규 사용자

1. 사용자가 Google 로그인을 시작한다.
2. Google 인증 성공 후 `googleSub`로 조회했지만 사용자가 없으면 계정을 생성하지 않는다.
3. Google 식별자, 이메일, 표시 이름을 담은 짧은 수명의 서명된 임시 가입 쿠키를 발급하고 프론트엔드 `/invite`로 이동한다.
4. 사용자가 공용 초대코드를 입력한다.
5. 백엔드는 임시 가입 쿠키의 서명과 만료를 확인하고, 입력값을 `INVITE_CODE`와 상수 시간 방식으로 비교한다.
6. 코드가 맞으면 동일 `googleSub` 사용자가 없는지 다시 확인한 뒤 계정을 생성한다.
7. 정식 JWT 쿠키를 발급하고 임시 가입 쿠키를 삭제한 뒤 `/onboarding`으로 이동한다.

## 백엔드 설계

### Google 로그인 성공 처리

현재 성공 핸들러가 항상 `upsertFromGoogle`을 호출하는 동작을 분리한다.

- 기존 사용자 조회와 신규 사용자 생성을 별도 서비스 메서드로 구분한다.
- 기존 사용자는 현재 JWT 발급 흐름을 그대로 탄다.
- 신규 사용자는 정식 JWT 대신 임시 가입 토큰만 발급한다.
- 초대코드 설정이 누락되어도 Google 인증 자체는 완료할 수 있지만, 신규 가입 완료 요청은 거부한다.

### 임시 가입 토큰

- 서버의 기존 JWT 서명 체계를 재사용하되 정식 로그인 토큰과 구분되는 용도 클레임을 둔다.
- Google `sub`, 이메일, 표시 이름과 만료 시각만 포함한다.
- 수명은 10분으로 제한한다.
- 별도의 HttpOnly 쿠키에 저장한다.
- 운영 환경에서는 기존 쿠키와 동일하게 Secure, SameSite, Domain 설정을 적용한다.
- 정식 인증 필터는 임시 가입 토큰을 로그인 토큰으로 인정하지 않는다.
- 쿠키 이름은 `invite_signup`으로 고정한다.

### 가입 완료 API

`POST /api/auth/invite/complete`

이 경로는 정식 로그인 전 호출할 수 있도록 Spring Security에서 공개하되, 유효한 임시 가입 쿠키를 자체적으로 반드시 검증한다.

요청:

```json
{
  "code": "공용 초대코드"
}
```

처리:

- 유효한 임시 가입 쿠키가 없으면 `401`을 반환한다.
- `INVITE_CODE`가 없거나 비어 있으면 `503`을 반환하며 신규 사용자를 만들지 않는다.
- 코드가 틀리면 `403`을 반환한다.
- 성공하면 사용자를 생성하고 정식 JWT 쿠키를 발급한다.
- Google 인증과 가입 완료 사이에 같은 사용자가 생성된 경우 기존 사용자로 처리해 중복 생성을 막는다.
- 성공 응답 후 프론트엔드는 `/onboarding`으로 이동한다.

### 요청 제한

- 초대코드 완료 API는 클라이언트 IP별 10분 동안 실패 5회로 제한한다.
- 여섯 번째 요청부터 10분 구간이 끝날 때까지 `429`를 반환한다. 성공하면 해당 IP의 실패 기록을 제거한다.
- 애플리케이션 인스턴스 메모리 안에서 동작하는 최소 구현으로 시작한다. Render 인스턴스 재시작 시 카운터가 초기화되는 점은 소규모 베타 범위에서 허용한다.
- 로그에는 입력된 초대코드와 임시 토큰 내용을 남기지 않는다.

## 프론트엔드 설계

- `/invite` 페이지에 초대코드 입력란과 가입 완료 버튼을 제공한다.
- Google 인증 성공 핸들러는 기존 성공 리다이렉트의 origin에 `/invite`를 붙여 신규 사용자를 이동시킨다.
- 성공 시 `/onboarding`으로 이동한다.
- 잘못된 코드는 다시 입력할 수 있도록 안내한다.
- 임시 가입 세션이 없거나 만료된 경우 Google 로그인을 다시 시작하도록 안내한다.
- 서버 설정 누락은 일반적인 입력 오류와 구분해 잠시 가입할 수 없다는 메시지를 표시한다.
- 로그인 랜딩 페이지와 기존 사용자 화면은 변경하지 않는다.

## 보안 및 실패 처리

- 초대코드는 소스 코드, 프론트엔드 번들, URL, 브라우저 저장소에 포함하지 않는다.
- 초대코드 비교는 길이 차이를 포함해 타이밍 정보가 최대한 드러나지 않도록 처리한다.
- 신규 사용자는 초대코드 확인 전 `users` 테이블에 저장되지 않는다.
- 임시 가입 쿠키로 일반 인증 API를 호출할 수 없다.
- 만료·변조된 임시 토큰은 가입을 완료할 수 없다.
- 환경변수 누락 시 실패 닫힘 방식으로 신규 가입만 차단한다.

## 테스트

백엔드 자동 테스트:

- 기존 Google 사용자는 초대코드 없이 로그인된다.
- 신규 Google 사용자는 생성되지 않고 `/invite`로 이동한다.
- 올바른 코드와 유효한 임시 토큰으로만 사용자가 생성된다.
- 잘못된 코드, 빈 코드, 만료·변조 토큰은 사용자를 만들지 않는다.
- `INVITE_CODE` 누락 시 신규 가입이 차단되고 기존 로그인은 유지된다.
- 동일 Google 사용자의 동시 가입 완료 요청이 중복 사용자를 만들지 않는다.
- 임시 가입 쿠키는 일반 JWT 인증으로 인정되지 않는다.
- 성공 시 임시 쿠키가 삭제되고 정식 JWT 쿠키가 발급된다.
- 반복 실패 시 요청 제한이 적용된다.

프론트엔드 검증:

- 초대코드 입력과 제출 상태가 정상 동작한다.
- 응답 상태별 안내 문구와 성공 리다이렉트가 올바르다.
- 타입 검사와 린트를 통과한다.

## 운영 설정

Render 백엔드 서비스에 `INVITE_CODE`를 설정한 뒤 배포한다. 코드 교체는 환경변수를 변경하고 재배포하는 것으로 처리한다. 프론트엔드에는 초대코드를 설정하지 않는다.
